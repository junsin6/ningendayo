# AI 日本語クセ分類体系 v1.2 (Japanese AI-Tell Taxonomy)

LLM（ChatGPT・Claude・Gemini など）が生成した日本語の文章に繰り返し現れる「AIっぽさ（AIクセ）」を、10 大分類 × サブパターンに整理する。検出器・推敲役・レビュアーが共有する唯一の信頼源（SSOT）。各パターンに (1) 定義、(2) シグネチャ例文、(3) 深刻度（S1 決定的 / S2 強い / S3 弱い）、(4) 推敲処方を付す。

> **設計思想**: 日本語の AIクセは **(1) 英語翻訳調 + (2) 過剰な丁寧体・敬語 + (3) カタカナ語の氾濫 + (4) 状態叙述（〜となっている）の機械的多用** という固有の重心を持つ。英語圏の humanizer はこの重心を捉えられない。本書は A〜J の 10 分類 × S1〜S3 の深刻度でこれを体系化し、日本語にしか存在しないパターン（過剰敬語・です/ます単調・カタカナ語）は **★日本語固有** と明記した。

## 深刻度の基準

* **S1 決定的 (critical)**: 一度出ただけで「これは AI」とほぼ確信させるパターン。無条件で除去。
* **S2 強い (high)**: 1〜2 回なら自然だが、文書内で 3 回以上反復すると露見する。密度ベースで除去。
* **S3 弱い (low)**: 単独では問題ない。他のパターンと重なったとき AI 印象を強める。リズム調整レベル。

## A. 翻訳調 (Translation-ese) — S1〜S2

英語の構文を日本語の語順・助詞体系に無理に移した痕跡。日本語 AI 文の最も決定的なシグネチャ。

### A-1. 「〜における / 〜においては」濫用 [S1]

* パターン: 場所・状況・分野を抽象的に枠づける（英語 `in / at / regarding`）。AI が「硬く・知的に」見せようとする基本動作。
* 例: 「ビジネス**における**意思決定」→「ビジネスの意思決定」/「現場で決めるとき」
* 処方: 「〜の」「〜で」に直結。または主題助詞「は」。一文書に「における」2 回以下。

### A-2. 「〜について / 〜に関して / 〜に対して」濫用 [S1]

* パターン: 主題提示（英語 `about / regarding / toward`）をほぼすべてこの形で処理。
* 例: 「AI 規制**について**議論する必要がある」→「AI 規制を議論すべきだ」
* 処方: 目的格「を」で直結、または主題「は」。

### A-3. 「〜を通じて / 〜を通して」濫用 [S2]

* パターン: 手段・経路をほぼ全部「通じて」で処理（英語 `through / via`）。
* 例: 「データ分析**を通じて**示唆を得る」→「データを分析して示唆を得る」
* 処方: 「〜で」「〜により」に分散。

### A-4. 「〜に基づいて / 〜をもとに」濫用 [S2]

* パターン: 根拠提示（英語 `based on`）。
* 例: 「データ**に基づいて**判断する」→「データから判断する」/「データを見て決める」

### A-5. 「〜することができる」濫用 [S1]

* パターン: 可能の冗長形（英語 `be able to / can`）。AI 文の最頻出シグネチャの一つ。
* 例: 「効率を高める**ことができる**」→「効率を高め**られる**」/「効率が上がる」
* 処方: 「〜できる」に短縮。可能性を主張する必要がない箇所は断定形（「高まる」）へ。

### A-6. 「〜となっている / 〜となります」状態叙述の濫用 [S1] ★日本語固有寄り

* パターン: 単なる「である／だ」で足りる箇所を、英語 `has become / it is the case that` 的に状態化。日本語 LLM の最強クセの一つ。
* 例: 「課題**となっている**」→「課題だ」/「重要**となります**」→「重要だ」
* 処方: 「だ／である」へ。変化を本当に言うときだけ「〜になった」。

### A-7. 「〜を持っている / 〜を有する」[S2]

* パターン: 所有・特性叙述（英語 `have / possess`）。
* 例: 「強い競争力**を持っている**」→「競争力が強い」
* 処方: 形容詞形に回して述語を消す。

### A-8. 「〜によって」受動文（by-passive）[S2]

* パターン: 英語受動態の直訳。行為者を「によって」で後置。
* 例: 「AI **によって**生成された画像」→「AI が作った画像」
* 処方: 行為者を主語に復帰させ能動文へ。

### A-9. 「〜のために」目的節の濫用 [S2]

* パターン: `in order to` の直訳。
* 例: 「顧客満足**のために**努力する」→「顧客に満足してもらえるよう取り組む」

### A-10. 抽象主語 + 万能動詞「〜を示している / 提供する / もたらす」[S1]

* パターン: 英語 `The X shows / provides / brings Y` の直訳。主語が事象・技術・概念で、述語が「示している・提供する・もたらす・意味する」。
* 例: 「この結果**は**重要性**を示している**」/「本技術**は**新たな価値**を提供する**」
* 処方: 主語を行為者（人・チーム・企業）に戻すか、主語・動詞ごと消して直接叙述。「この結果から〜がわかる」式。

### A-11. 名詞の羅列（助詞の欠落 / 「の」の連鎖）[S2]

* パターン: 英語の名詞句を助詞なし、または「の」を 3 つ以上連ねて接続。
* 例: 「AI 技術発展速度加速化」→「AI 技術の発展が速まっている」/「企業の製品の品質の向上」→「企業が製品の品質を高める」
* 処方: 適切な助詞（が・を・で）を復元。「の」連鎖は 2 つまで。

### A-12. 二重否定「〜なくはない / 〜ないとは言えない」[S2]

* パターン: 英語 `not un-` 的な回りくどい肯定。
* 例: 「効果が**ないとは言えない**」→「効果はある」/「効果が見込める」
* 処方: 肯定で断定。本当に留保が要る箇所のみ残す。

### A-13. 「〜という」過剰連結 [S2]

* パターン: 名詞・引用・概念をすべて「という」で接続（英語 `that / so-called`）。
* 例: 「持続可能性**という**概念」→「持続可能性（という概念）」→ ほとんど削除可
* 処方: 「という」の大半を削除。本当に引用・定義する箇所だけ残す。

## B. 英語引用・カタカナ語の過多 — S2 ★日本語固有寄り

### B-1. 括弧併記の習慣 [S2]

* パターン: 初出のすべての専門語に英語を併記。
* 例: 「人工知能**（AI）**は大規模言語モデル**（LLM）**とは異なる」
* 処方: 専門読者向けなら 1 回だけ併記、以後は日本語（またはカタカナ略語）。一般読者向けなら英語併記自体を最小化。

### B-2. カタカナ語の濫用 [S2] ★日本語固有

* パターン: 日本語で書けるのに不要なカタカナ語・英語を多用。AI 文の知的偽装によく出る。
* 例: 「この**フレームワーク**を**レバレッジ**して**シームレス**に」→「この枠組みを活かして滑らかに」
* 頻出: leverage→活用、framework→枠組み、robust→堅牢、insight→示唆、commit→注力、agenda→課題
* 例外: 固有名詞・業界標準語（Transformer・API・SDK・トークン 等）は維持。

### B-3. 英語引用句の生埋め込み [S2]

* パターン: 英文を引用のまま挿入し訳も併記。
* 処方: 原文のニュアンスが本当に必要な場合以外は日本語に開き、出典だけ併記。

## C. 構造的 AI パターン（書式・レイアウト）— S1〜S2

### C-1. 機械的な並列列挙「まず・次に・最後に / 第一に・第二に」[S1]

* パターン: 「まず、〜。次に、〜。最後に、〜。」が段落全体を支配。
* 処方: 3 つのうち 1〜2 つを叙述文に溶かす。列挙が必要なら各項目の長さ・構造をわざと崩す。

### C-2. 過度な箇条書き [S2]

* パターン: エッセイ・コラム・レポートで 3 つ以上連続する箇条書きブロック。
* 処方: 箇条書きを散文に「溶かす」。本当に列挙が効く箇所だけ残す。

### C-3. 反復的なセクション見出し「導入・本論・結論」[S2]

* パターン: 図式的な分節。
* 処方: 散文ならば見出し自体を削除。レポート型なら見出し文を具体化（「AI 規制の三つの亀裂」）。

### C-4. 段落冒頭の要約文公式（topic sentence）[S2]

* パターン: 各段落の最初の一文がその段落の要約。英語作文教本式。
* 処方: 一部の段落は事例・場面・引用から始めて順序を崩す。

### C-5. 絵文字の濫用 [S1]

* パターン: ✅🚀💡⚠️📊 などがリストの頭・見出し・強調に埋め込まれている。
* 処方: エッセイ／レポート文脈なら全削除。SNS・製品コピー以外では AIクセが極端に強い。

### C-6. 見出し直後の一行要約ボックス [S2]

* パターン: すべての見出し直後に「本セクションでは〜を扱います」式の案内文。
* 処方: 削除。本文がすぐ始まるのが日本語の文章らしい。

### C-7. 段落冒頭「一方 / しかし / 結局」公式の連発 [S2]

* パターン: 段落冒頭が順に「一方〜／しかし〜／結局〜」で固定。3 連続以上で AI 特有。
* 処方: 3 つのうち 2 つを削除。順序の意味は段落の流れで伝える。接続詞なしで始まる段落も混ぜる。

### C-8. 対称的対句「Aか、Bか」の反復 [S2]

* パターン: 同一文書で二項対立が 3 回以上、平行構文で反復。英語修辞の直訳。
* 例: 「独占**か**、拡散**か**」「戦略家には〜、立案者には〜」
* 処方: 3 つのうち 2 つを非対称に再配置。一方を問い・他方を叙述に混ぜる。

## D. AI 特有の慣用句（Signature Phrases）— S1

日本語の人間の書き手はほぼ使わないが、LLM が反復的に産出する常套句。発見即交換。

### D-1. 結び・要約類

* 「結論として」「まとめると」「総括すると」「整理すると」
* 「〜と言えるだろう」「〜と言えます」「〜と言えるでしょう」
* 「〜に他ならない」
* 「いかがでしたでしょうか」（ブログ AI の決定的シグネチャ）

### D-2. 意義・重要性の誇張

* 「非常に重要である」「必ず押さえておきたい」
* 「示唆に富む」「注目に値する」「見逃せない」
* 「〜の地平を開く」「〜に一石を投じる」
* 「意義深い」「重要な意味を持つ」

### D-3. 列挙の導入

* 「大きく三つに分けられる」
* 「以下のような特徴を持つ」
* 「次のように整理できる」

### D-4. ハイプ語彙

* 「革新的な」「画期的な」「前例のない」「まさに〜」
* 「〜の可能性を切り開く」
* 「〜の新たな時代が到来した」
* 「〜は欠かせない」

### D-5. 擬人化された抽象主語 [S2]

* パターン: 事象・技術・概念を主語に、人間の行為のように叙述。
* 例: 「**二つの知能の衝突**が問い**を投げかける**」「**AI 競争**が**終わらない**」
* 処方: 実際の行為者へ主語を交換（「両社の競争は」「エンジニアたちは」）、または擬人化動詞を弱める（「投げかける」→「残る」「生まれる」）。象徴的な見出し・要約での 1 回程度は許容。

### D-6. 完結公式型の結び「〜すべき時だ / 〜していく必要がある」[S2]

* パターン: コラム・レポート末尾が「〜すべき時です」「〜へと進む時だ」「〜が求められています」公式。
* 例: 「次の段階へ**進むべき時です**」
* 処方: 同義を具体動詞の断定に。「次の段階へ**移る**」程度まで許容（誇張が弱い）。一文書に一度だけ。

**処方:** 大半は **削除**。意味が必要なら具体的な名詞・動詞へ置換（「重要だ」→「核心だ」または具体的根拠で）。

## E. リズム・文長の均一性 — S2

### E-1. 文長の標準偏差が低い

* すべての文が 40〜60 字付近に集中。
* 処方: 意図的に短文（10〜20 字）を段落ごとに 1〜2 個挟む。長文（90 字+）も 1 つ混ぜる。

### E-2. 「です・ます」体／「だ・である」体の単調反復 [S2] ★日本語固有

* パターン: 「〜です。〜です。〜です。」または「〜である。〜である。」が連続。文末が一本調子。
* 処方: 体言止め・「〜だ」「〜のだ」「〜だろう」「〜た」を混ぜる。日本語の書き手は無意識に文末を変奏する。です・ます体なら時折「〜ます」を体言止めや「〜でしょう」に。
* 注意: 文体（敬体／常体）そのものは原文を維持。混在させて崩すのではなく、同一文体内での変奏を指す。
* mixed（混在文体）での評価基準: E-2 は文書を register ゾーンに分割し、**各ゾーンをそのゾーンの文体基準で個別に評価**する（敬体ゾーンは です・ます の単調で、常体ゾーンは だ・である の単調で判定）。ゾーン間の敬体⇄常体の交替を「文末変奏」として加点してはならない（混在で E-2 を稼ぐのを防ぐ）。`score_before`/`score_after` の E-2 改善は register 内でのみ測定する。type B（不統一）ゾーンは統一による変奏を行わず、各平叙文をその文の register で局所的に減点評価する（詳細は検出出力スキーマ節の `style: "mixed"` 定義を参照）。

### E-3. すべての段落が 3〜4 文公式

* 段落の長さも均一。
* 処方: 1 文段落 / 6 文段落を意図的に混ぜる。

## F. 過度な修飾・重複 — S2

### F-1. 程度副詞中毒

* 「非常に」「とても」「極めて」「まさに」「大変」
* 処方: 大半を削除。強調が必要なら具体的な数値・事例で代替。

### F-2. 同義語の二重修飾

* 「重要かつ中心的な役割」
* 「新しく革新的なアプローチ」
* 「継続的で着実な努力」
* 処方: 二つの修飾語のうち一つだけ残す。

### F-3. 機能 + 役割の複合句

* 「〜としての役割と機能」
* 「〜の意味と価値」
* 処方: 一つだけ。

### F-4. 「〜的」「〜性」「〜化」の濫用 [S2]

* パターン: 抽象接尾辞の多用。
* 例: 「**根本的**な観点で**構造的**変化が**不可避**だ」→「構造が根本から変わる」
* 処方: 「〜的」を (a) 動詞句、(b) 具体名詞へ解体。一文書での「〜的 N」密度を半分以下に。

### F-5. 「〜性」抽象名詞の連鎖 [S2]

* パターン: 「N 性」が一文書に 3 回以上反復し、形容詞・動詞で足りる箇所を名詞化。
* 例: 「拡張**性**」「安定**性**」「持続**性**」「優位**性**」が並ぶ
* 処方: 動詞・形容詞へ開く。「拡張性が高い」→「よく拡張できる」。一文書で「〜性」2〜3 回以下に。

## G. 過度なヘッジング（婉曲）— S2

### G-1. 推測・観測型の文末

* 「〜と考えられる」「〜と思われる」「〜と見られる」
* 「〜のように見える」「〜ではないだろうか」
* 「〜と言えるかもしれない」がすべての文末に付く
* 処方: 断定できる箇所は断定。ヘッジングは本当に不確実な箇所だけ。

### G-2. 二重・三重の婉曲

* 「〜する可能性があると考えられる」
* 「〜と見ることもできるだろう」
* 処方: 一つだけ残す。

---

## H. 接続詞の多用 — S2

### H-1. 文頭接続詞の過多

* 各文・各段落の冒頭に「また」「したがって」「つまり」「さらに」「なお」「加えて」「そして」
* 処方: 70% 以上削除。論理の流れは文の内容自体で示す。本当に逆接・因果を強調するときだけ。

### H-2. 「しかし」「だが」逆接の濫用

* 逆接が段落ごとに登場。
* 処方: 半分以上削除。対比が自明なら接続詞なしで通る。

### H-3. 「これは〜」指示の反復

* 「これは〜を意味する」
* 処方: 前文とつなげるか、具体叙述へ置換。

### H-4. 再定義の「つまり / すなわち」濫用 [S2]

* パターン: 英語 `i.e. / that is` の直訳。補足が要るたびに頭に付ける。
* 例: 「AI の民主化、**つまり**経済性の面で」
* 処方: 「言い換えれば」「要は」などへ語彙変奏。または省いて読点でつなぐ。一文書に 2 回以下。

## I. 形式名詞・形式的表現の過多 — S2

### I-1. 「〜こと / 〜ということ」濫用

* 「〜することが重要だ」「〜ということだ」が段落の代表文末。
* 処方: 断定叙述へ。「重要だ」へ直結。

### I-2. 「〜という点 / 〜という面 / 〜という意味で」反復

* 「注目すべき**点**は」「〜という**面**では」
* 処方: 具体名詞・動詞へ置換または削除。

### I-3. 「〜する必要がある」[S2]

* 英語 `should / need to` の直訳。
* 処方: 「〜すべきだ」または具体的な勧告形へ。

### I-4. 「〜が求められる / 〜が必要だ」[S2] ★日本語固有寄り

* パターン: 行為者を曖昧にしたままの要請。日本語ビジネス AI 文の最頻出常套。
* 例: 「変革**が求められる**」「対応**が必要だ**」
* 処方: 誰が何をすべきかを主語・動詞で具体化。「企業は変わらなければならない」。

### I-5. 「〜能力 / 〜力」抽象名詞の連鎖 [S2]

* パターン: 「N 能力」「N 力」が一文書に 3 回以上反復し、動詞の代わりに名詞句で能力を叙述。
* 例: 「思考**能力**」「長文脈の保持**能力**」「推論**力**」
* 処方: 動詞形に開く。「思考能力が高い」→「よく考えられる」。一文書で 2 回以下に。

## 検出出力スキーマ（Detector → Rewriter の共有契約）

検出器は次の JSON を生産する:

```json
{
  "meta": {
    "input_length": 1820,
    "detected_count": 37,
    "ai_tell_density": 0.203,
    "raw_weighted_score": 75.5,
    "severity_weighted_score": 71.6,
    "style": "desu_masu"
  },
  "findings": [
    {
      "id": "f001",
      "category": "A-6",
      "category_label": "翻訳調: 〜となっている 状態叙述の濫用",
      "severity": "S1",
      "scope": "span",
      "text_span": "課題となっている",
      "start": 142,
      "end": 150,
      "reason": "「となっている」が本文で6回反復し状態叙述が機械的",
      "suggested_fix": "課題だ"
    },
    {
      "id": "f020",
      "category": "E-2",
      "category_label": "リズム: です・ます単調反復",
      "severity": "S2",
      "scope": "document",
      "text_span": "果たします",
      "start": 610,
      "end": 615,
      "occurrences": [[88, 92], [255, 259], [610, 615]],
      "reason": "文末の85%が「ます／です」。text_span は代表アンカーで、実改変は occurrences 全体に及ぶ",
      "suggested_fix": "文末を体言止め・〜でしょう・〜た等へ変奏"
    }
  ],
  "category_summary": {
    "A": 12, "B": 3, "C": 2, "D": 8, "E": 1,
    "F": 4, "G": 2, "H": 3, "I": 1, "J": 1
  }
}
```

* `raw_weighted_score`: S1=5, S2=2, S3=0.5 の**素の加重和（正規化前）**。絶対比較・run 間の回帰検証・改善率の内訳確認に使う。検出器は必ず併記する。
* `severity_weighted_score`: `raw_weighted_score` を飽和しにくい対数圧縮で 0〜100 に正規化した値。
  * 式: `severity_weighted_score = round(100 * (1 - exp(-raw_weighted_score / K)), 1)`、**K = 60（固定・input_length 非依存）**。
  * 例: raw 75.5 → 71.6 ／ raw 15 → 22.1 ／ raw 200 → 96.4。高密度短文でも 100 に張り付かず解像度を保つ（旧「raw×1000/長さ」方式の飽和欠陥を解消。IMP-002）。
  * 上限は理論上 100 に漸近するのみで実際には飽和しない。
* `score_before` / `score_after` の契約: naturalness-reviewer は `score_before = 02_detection.json の meta.severity_weighted_score`、`score_after` は推敲後テキストに**同じ式・同じ K=60**を適用して算出する。K を固定し input_length に依存させないため、before・after はともに入力長非依存の同一関数値であり、改善率 `(before−after)/before` も入力長に依存しない（スケール不変）。※対数圧縮は非線形関数のため、旧「raw×1000／長さ」方式のように「正規化係数がキャンセルする」のではなく、「正規化式そのものが入力長を含まない」ことがスケール不変の根拠である（IMP-003）。
* `ai_tell_density`: 検出 span の**重複除去後のユニーク被覆文字数** / 全体文字数。算入規則は次の通り: (1) `occurrences[]` を持つ finding はその全 span の和集合を被覆に算入し、代表アンカー（`text_span`/`start`/`end`）は occurrences に含まれる前提のため別途加算しない。(2) `occurrences[]` を持たない finding は `[start,end]` を用いる。(3) 全 finding の span を文書全体で和集合化（重複・入れ子を除去）してから全体文字数で割る。これにより重複 span・文書レベル locator を二重計上しない（IMP-004）。
* `scope`（finding 単位, 既定 `"span"`）: `"span"` = 連続する単一箇所。`"document"` = 文書全体の分布が根拠のパターン（E リズム／C-1・C-7 構造／H-1 接続詞連鎖 等）。`scope:"document"` の finding は `text_span`/`start`/`end` を**代表アンカー**とし、任意の `occurrences: [[start,end],...]` に実該当箇所を列挙する。推敲役は `scope:"document"` の finding について reason・occurrences が示す全 span を改変対象としてよい（「検出のない区間は触らない」の例外）。
* `style`: 入力文体。`desu_masu`（敬体: です・ます基調）/ `da_dearu`（常体: だ・である基調）/ `mixed`（混在。下記定義）。推敲役は原文の文体を必ず維持し、局所文体を勝手に支配文体へ寄せない。
* `style: "mixed"` の定義と扱い（v1.2 追加。監査第13項・E-2 判定の基準）:
  * **定義**: 一文書内に敬体（です・ます）と常体（だ・である）が併存する状態。次の 2 型を区別する。
    * **type A 構造的混在（自然）**: 支配文体が存在し、非支配文体は見出し・箇条書き断片・体言止め・鉤括弧内の引用・括弧補足・地の文中の内言／格言など、局所的に正当化される用法に限定される。日本語の書き手も普通に行う。
    * **type B 不統一混在（欠陥）**: 同一階層の連続する地の文（平叙文）で敬体と常体が無秩序に交替する。書き手不在の兆候であり軽度の AI tell でもある。
  * **文体保存ポリシー**:
    * type A → **そのまま保存**。非支配文体の局所ゾーンを支配文体へ変換しない。
    * type B → **推敲役は独断で統一しない**。敬体⇄常体の統一は「文体変更」に当たり鉄則3（文体維持）違反となるため AI-tell 除去の範囲外とする。detector は type B を finding として上げ、オーケストレーターは `hold_and_report`（人間レビュー）で「どちらの文体へ寄せるか」を委ねる。人間の明示指示がない限り原文の混在を保存し、各 register ゾーン内でのみ他の AI-tell 除去（E-2 変奏を含む）を行う。
  * **推奨 meta 併記（mixed 時）**: 任意フィールド `style_profile: { "dominant": "desu_masu"|"da_dearu", "type": "A"|"B", "zones": [{"start":_, "end":_, "register": "desu_masu"|"da_dearu"}] }` を出力してよい。監査第13項（文体タグ保存）は zones 単位で before/after の register 一致を検証する。mixed を単一タグで突き合わせず、ゾーン対応で監査する。
